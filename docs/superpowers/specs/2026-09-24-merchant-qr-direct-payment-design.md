# Merchant QR Direct Payment Design

## Goal

When a recipient scans a payment QR generated by N42 Wallet, the app should
open the payment form for the exact chain and asset encoded by that QR. A QR
without a requested amount should leave the amount field editable. A QR with a
valid requested amount should continue to prefill that amount using the
existing send-form behavior.

This addresses the current flow where a QR containing only an address loses
its asset identity and opens the coin picker. A bare address entered or scanned
outside an asset-aware payment QR remains ambiguous and continues to open the
coin picker.

## User-visible behavior

- Every N42-generated receive QR carries enough information to identify its
  native coin or token and chain, whether or not an amount is set.
- Scanning an asset-aware QR from the wallet home opens `WalletChainSend` with
  the matching asset and recipient already selected.
- An absent amount is passed as `null`, so the sender can enter an amount.
- A valid specified amount is converted to display units and passed to the
  sender. Existing positive-amount locking behavior remains in effect.
- Unknown, malformed, or unsupported asset-aware requests show the existing
  unsupported-request feedback and do not silently select a different asset.
- Legacy QR codes containing a plain address retain the current coin-picker
  flow.

## Design

The receive-QR builder will produce a chain-aware payment request for every
asset. It will prefer an established chain payment URI when that URI carries
enough identity for N42 Wallet to resolve the exact chain and asset. EVM native
coins use EIP-681 with an explicit chain ID; ERC-20 requests identify the token
contract and recipient, with the amount omitted when unset. For native BTC,
SOL, TON, TRX, XRP, Cosmos, and NEAR requests, retain the corresponding existing
`bitcoin:`, `solana:`, `ton:transfer/`, `tron:`, `xrpl:`, `cosmos:`, and `near:`
URI forms, omitting `amount` when unset. If a format cannot unambiguously
identify the chain, network, or token (including non-EVM tokens whose standard
URI omits token identity), the builder uses this versioned N42 URI:

```
n42pay://v1/pay?chain=<chain-mKey>&network=<mainnet|testnet>&type=<native|token>&to=<recipient>[&contract=<token-contract>][&amount=<decimal>]
```

`chain`, `network`, `type`, and `to` are required. `contract` is required for
tokens and forbidden for native coins. `amount` is an optional positive decimal
in display units, without locale separators. All query values are
percent-encoded. The on-screen address and copy-address action continue to
expose the plain wallet address.

The scan flow will normalize recognized payment URIs into one request model:
chain/network identity, native-or-token identity, recipient, and optional
amount. Asset resolution will match chain ID for EVM requests; N42 requests
will match chain `mKey` plus network and, for tokens, the network-specific
contract. The resolved request will reuse the existing send form; no separate
payment execution path is introduced. Unsupported or ambiguous requests will
never be guessed from address shape alone.

## Components

- `wallet_receive_qr.dart`: create amount-free and amount-bearing asset-aware
  payloads for the selected native coin or token.
- `eip681.dart` and a chain-payment URI parser: represent and parse EIP-681,
  N42, and the supported established request formats, including requests
  without amounts.
- `scan_to_pay_utils.dart`: resolve a parsed request against wallet-owned
  native coins and tokens, returning the asset, recipient, and optional amount.
- `wallet_page.dart`: dispatch recognized requests directly to
  `WalletChainSend`, preserve WalletConnect routing, and retain the existing
  selector for plain addresses.

## Compatibility and failure handling

Existing plain-address QR codes remain supported. Existing EIP-681 requests
remain supported, including explicit chain IDs and optional amounts. Receive
QR display, address copying, and sharing of the plain address are unchanged.
Payment requests with malformed values, unknown chains, unknown token
contracts, or missing required identity fields fail closed with the existing
unsupported-request message. The scanner must not fall back to a different
asset when a recognized payment URI fails resolution.

## Acceptance criteria

1. Scanning an N native-coin QR without an amount opens the N send form with the
   recipient set and amount editable, without showing the coin selector.
2. Scanning an N native-coin QR with an amount opens the N send form with that
   amount prefilled and follows current positive-amount behavior.
3. Scanning supported token QR payloads resolves to the same token and chain
   selected on the receive page.
4. A legacy plain-address QR still opens the coin selector.
5. An unsupported asset request cannot be misrouted to another wallet asset.
6. WalletConnect QR routing remains unchanged.

## Scope

This change covers payment QRs generated by N42 Wallet and scanned through the
wallet-home scan-to-pay action. It does not change the standalone receive-page
currency selector, transaction submission/signing, or external merchant QR
formats that do not carry an asset identity.
