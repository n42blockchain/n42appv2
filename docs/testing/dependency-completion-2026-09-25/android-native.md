The [upstream Web3j Android family](https://github.com/LFDT-web3j/web3j), 4.12.3-android as of the 2026-09-26 review, was evaluated. Its `abi`, `crypto`, and `tuples` AARs all publish manifest namespace `com.org.web3j`, which AGP 9.4.1 rejects when the complete family is present. The upstream Android AAR POMs also omit the module dependency edges, so six modules had to be specified for the candidate. The exact failing merger and published AAR manifest hashes are in `logs/harness-security-verify-attempt3.log` and `logs/web3j-namespace-evidence.txt`. Repackaging three vendor AARs and manually maintaining their missing dependency edges would create a larger unverified binary fork. The host therefore retains the coherent, working Web3Auth transitive Web3j 4.8.8-android family. Remove this cap when the upstream Android modules publish distinct namespaces and complete metadata, then rebuild and rerun Web3Auth/Torus signing, address, serialization, and release R8 checks. The Java Web3j line is not a drop-in Android substitute.

The public-coordinate OSV scan for the exact final graph selected 316 unique Maven coordinates: 101 confirmed Maven Central and 203 confirmed Google coordinates were queried through OSV, with HTTP 200, no pagination and zero matched advisories. This includes remediation of the earlier selected Jackson, protobuf, BC, and Java-WebSocket versions. Twelve selected coordinates were excluded because their private/JitPack/Torus/Flutter-engine advisory coverage was not established; opaque local AAR contents are outside the coordinate total. The archive's `security/` folder retains public-coordinate request, response, provenance and refined coverage JSON. This is a scoped public Maven scan, not whole-app security clearance.

## Native runtime and release artifacts

The Android sqlite3 hook uses `source: system`, `name: sqlcipher`, and the host selects the Zetetic 4.19.0 AAR rather than sqflite_sqlcipher's older 4.10.0 request. There is one `libsqlcipher.so` per shipping ABI and no `pickFirst`. The arm64 library in the Maven AAR, release AAB and release APK has identical SHA-256 `da51355b6c455150dae59e902c484292d33d752b7fec36f723558625d88048fa` (AAR SHA-256 `3f2aeebb584157baf145805dd8e2118a093632fbfa3dcb72a39e43a2c56b41fe`). This establishes packaged provenance; runtime behavior was tested separately.

The committed isolated harness uses app ID `com.n42.android_native_smoke`, with no wallet app install or account data. On emulator-5554 (API 36, `getconf PAGE_SIZE=4096`), its seed run asserted SQLCipher 4.10.x and created a keyed database plus plaintext archive. Without uninstalling the app, the 4.19.0 verification run confirmed `PRAGMA cipher_version` 4.19.x, correct-key access to the old encrypted file, wrong/missing-key failures, `sqlcipher_export` migration, a plaintext `MatrixSdkDatabase`, and a Vodozemac Megolm roundtrip. It also passed Bouncy Castle 1.86, Web3j address/Keccak/signature recovery, the full published BIP39 mnemonic seed, BIP32 vector 1's fixed `m/0H` private key and Ethereum address, MediaPipe 0.10.35 generated-lite serialization/parse with protobuf 4.36.2, Java-WebSocket 1.6.0 loopback handshake/echo, and historical CallKit `ArrayList<Data>` JSON parse. The old BC 1.68 and new 1.86 runs produced byte-for-byte identical Torus addresses for two fixed keys through both private- and public-key APIs. In the inspected Web3Auth SDK, session manager and Torus utility bytecode, production TorusUtils/NodeUtils call the public-key address API; the private-key API has no external caller. Its surprising result for raw scalar input is unchanged upstream behavior, not a provider regression. The isolated app was uninstalled after the tests.

The AAB is 493.1 MB and the APK is 741.6 MB as reported by Flutter; neither file size is the Play device download size. Bundletool 1.18.3 estimated 156,504,821 compressed bytes (about 149.3 MiB) for the API 36 arm64 emulator specification. Actual all-device Play delivery and limits require Play Console verification in the final release task.

The final release artifacts contain Flutter engine, `libapp.so`, Vodozemac and SQLCipher in all three shipping ABIs: arm64-v8a (31 libraries), armeabi-v7a (21), and x86_64 (24). The earlier explicit release `abiFilters` had advertised x86 despite missing Flutter engine/app/Vodo there; removing that filter restored Flutter's three supported release ABIs without dropping a working architecture. Trust Wallet Core, WebRTC, Rust MLS, `libgojni`, Vodozemac and SQLCipher appear in all three. No separate `libc++_shared.so` is packaged. The local mining AARs have no verified upstream version/build provenance: `android/app/libs/mobile-sdk-android.aar` SHA-256 `97ab0b5e9665998f4387e09b812db4b05116ab9d49244182ccd2e8a1cba75646`, plugin `mobile-sdk-release.aar` `784783d758533826a768bc0697525d9b28caa857a3f4819707877fb790d6b254`, and both EVM AAR copies `28a8f91311b94b0ffaeea61620fa065633d0e8934b95c4250314c120775eb470`.

The app's compile-only mobile SDK AAR and the plugin's packaged runtime AAR each expose `Api` and `NativeBindings`. The JVM descriptors for all five methods called by host/plugin source match exactly. The compile-only AAR additionally exposes `genBlockVerifyResult(String,String)`, absent from the runtime AAR; current source does not call it. Both AARs have `libmobile_sdk.so` only for arm64/x86_64. `NativeBindings` loads that library when a mining API is first called; plugin registration and `MiningHandler` construction do not call it. On armeabi-v7a, a mining API call therefore reaches a missing native library and raises `UnsatisfiedLinkError`; the existing method handlers catch `Exception`, which does not catch this `Error`. This is a static call-path finding, not a measured 32-bit device crash. The existing plugin unit task passes one `getPlatformVersion` case, which does not execute any mining API. Supplier identity, native mining behavior, and a 32-bit capability gate remain Task 16 follow-up; no validator operation was run.

The merged release manifest has 66 components, no explicit `android:process` or `isolatedProcess`, `allowBackup=false`, and `@xml/data_extraction_rules`; cloud backup and device transfer exclude shared preferences, databases and files. This supports the secure-storage adapter's process-wide serialization assumption for the current merged manifest. Billing permission and foreground-service declarations are present. Billing 9.1.0 compiled and passed release R8; this is not purchase-flow acceptance. The later product clarification withdraws paid points and their sandbox gate. Task 17 now audits actual charging exposure and removes confirmed unused payment dependencies; any independently supported paid feature would require its own sandbox evidence. Foreground-service declarations and permission policy need Task 16 review. The 4 KB emulator did not establish 16 KB runtime behavior; Task 16 must run an isolated 16 KB device with compatibility fallback disabled where applicable. No host APK was installed on the emulator, and no production app data or physical device was touched.
