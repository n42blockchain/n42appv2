# Maintained Camera Core 1.6.1 surface JNI source

`upstream/` contains exact AndroidX support revision `987b9ac8585b31424a397206c492196dd163997b` native files, not a floating branch. Google's Gitiles directory JSON at that revision names blob IDs `e2e34ae21772951f5b86053dcf58c0e695ace0d6` (`CMakeLists.txt`), `d2a8437e5591bedc368bb4b5caaca8f46f8928ea` (`surface_util_jni.cc`) and `e324a17b1092f1364cdae330841eca9dbca5a728` (`jni.lds`). The retained source bodies reproduce those Git blob IDs and have SHA256 `6506d3c4...`, `dd3f0271...`, and `b578ca06...`, respectively. `LICENSE.txt` is the unmodified Apache-2.0 notice from the official 1.6.1 sources JAR, SHA256 `809fa1ed21450f59827d1e9aec720bbc4b687434fa22283c6cb5dd82a47ab9c0`. The upstream C++ and CMake retain their Apache headers.

The parent `CMakeLists.txt` is a maintained standalone overlay for **only** `surface_util_jni`. Upstream top-level CMake also configures `image_processing_util_jni` and requires libyuv even when building one target. The overlay uses the exact upstream C++ and `jni.lds`, links Android `libandroid`, retains maximum page size and adds common page size 16384 at the final link. The Android STL is `c++_static` to supply the upstream C++ headers. The NDK linker checks version-script names by default; `--undefined-version` permits the upstream script's optional `JNI_OnLoad` and `JNI_OnUnload` names, which this target does not define. Actual linked dependencies and exports must be compared with the official AAR. This overlay does not rebuild or alter the published image-processing JNI members, Java classes, resources or CameraX dependency metadata.

Run `scripts/build_camera_surface_android.sh --preflight` and then `--build` with the host's selected SDK/NDK. The script pins NDK28.2.13676358, CMake3.22.1, Android API23, the complete upstream file set and overlay/tool binary hashes, and builds all four published ABIs in the ignored task workspace. It retains unstripped build outputs and uses the pinned NDK `llvm-strip --strip-unneeded` for the candidate `jni/` members. This is a maintained candidate source build. The official Maven AAR has no producer attestation tying its bytes to this NDK or exact source revision; packaging/runtime acceptance is separate.

## Maintained Camera Core 1.6.2 module

The app selects stable CameraX 1.6.2 as one atomic family. The tracked Maven module under `maven/androidx/camera/camera-core/1.6.2/` starts from the official 1.6.2 AAR (SHA256 `ebd66f090414f4c12f23a55b5023aeee1b096da8a06c02a0b6fb3520c4ddadf6`). `scripts/build_camera_core_maven.py` checks that official AAR, POM and module metadata, checks every referenced auxiliary artifact, then replaces only the four `libsurface_util_jni.so` members with the accepted `candidate4.json` hashes. It preserves the other 24 AAR entries bytewise, including 1.6.2 `classes.jar`, all image-processing JNI members, resources and notice. It updates the AAR size and all four digests in both API and runtime `.module` file entries; other variants, dependencies and atomic-family constraints are unchanged.

The 1.6.2 official JNI surface members match 1.6.1 bytewise. The pinned `987b9ac...` C++ is an independently verified 1.6.1-boundary source basis for this maintained 1.6.2 binary, not an attestation of the supplier's original 1.6.2 producer revision or toolchain. Changing the build output path may change only the 20-byte GNU build ID; the accepted four binary hashes and packaged AAR are fixed here. A future source rebuild with different bytes requires fresh ABI, static, and runtime review.

Gradle's exclusive repository filter applies only to `androidx.camera:camera-core:1.6.2`; camera2, camera2-pipe and lifecycle resolve from the official repositories. The app's explicit Core 1.6.2 dependency raises the transitive CameraX family from `mobile_scanner`'s 1.6.1 request. The synthetic Surface fixture and final app package checks are separate acceptance gates.
