`checks/alignment-details.json` shows baseline LOAD true and GNU_RELRO false for both 64-bit libraries (RELRO end offsets 12288 arm64, 4096 x86_64). Both selected LOAD and RELRO pass. `checks/staged-audit.json` is the packaged staged-library ZIP audit, 2/2 pass. The 24 JNI/C export names match the baseline for every ABI (`checks/exports-*.txt`). Baseline static failure was not observed as a load crash in the strict runtime fixture.

The original and selected arm64 libraries each passed the same synthetic standalone JNI test under emulator-5560, `PAGE_SIZE=16384`, linker `fatal`, compatibility disabled. Final runs each have 17 `PASS` assertions and the `MLS_FIXTURE_PASS` sentinel; early fixture runs had 16 assertions before the explicit process architecture check. The fixture covers key package, add/welcome, bidirectional encryption/decryption, self-update/commit, and invalid input. `runtime/*-inputs.txt` binds the library and DEX hashes to host/device input and pre/post strict settings. `runtime/*-jni.log` includes the mapped library. Normalized semantic output is equal; randomized cryptographic output bytes were not compared.

The final installed synthetic APK is `apk/signed-synthetic-fixture.apk`, SHA256 `92700b00722cf34d99318dfec426c1852954b3b92f2a1d56afd57d65494a7b22`. Its installed device SHA matched exactly. The selected native member SHA equals the selected arm64 library; it is uncompressed at ZIP data offset `0x4000`, verified 16 KB aligned. `apk/mapping-verification.json` binds that local-entry offset plus executable ELF LOAD offset to observed `base.apk` process map offsets `0x4000` and `0xa8000`. The APK passed `zipalign -P 16`, APK signature verification, static ELF audit, and the real JNI flow (`MLS_APK_FIXTURE_PASS`). The APK uses a disposable synthetic signing key; the private keystore is excluded from this archive. It is an isolated test APK, not the signed main app release.

`checks/apk-verifier-controls.json` records Python optimized-mode positive result 0 and three negative results 1 for a shifted executable map, missing success marker, and wrong selected library. Build preflights refused an existing stage, wrong NDK, wrong Rust compiler, and initially missing Rust 32-bit targets. The wrong-page-size fixture control refused before device work. `build/rust-tests.log` records 6/6 locked offline Rust tests. Commands and raw logs are retained under `build/`, `runtime/`, and `apk/`; `manifest.json` records their SHA256 values. Run `python3 verify_evidence.py` from this directory to recheck tracked inputs, file hashes, selected binaries, and the archived APK/mapping proof. The validator uses explicit failures under optimized Python as well.

The first APK prototype failed its **fixture mapping assertion** because Android maps the native member as `base.apk` rather than a path containing `libn42_mls.so`; it was not an SDK load failure (`history/prototype-map-failure.log`). A later recipe attempt failed installation because an earlier synthetic package had a different disposable signer (`history/first-recipe-install-failure.log`). The next attempt installed but the runner exited before logging due an immediate `pidof` race; the runner now retries. Final `apk/` files are from the subsequent clean `run_apk.sh` success and supersede those attempts. An early shell wrapper for printing negative-control tails exited 127 after losing `tail` from that shell's PATH; the individual preflight commands had the recorded nonzero results. These errors are retained as fixture and evidence limits, not classified as native-library failures.

The build itself used Cargo `--offline`; the JNI fixtures contain no network operations. This record does not establish that all emulator network interfaces were disabled. It does not establish 32-bit device runtime, main-app release APK/AAB selection, other Task16F native libraries, or full application behavior. Whole-package acceptance follows the other native-family repairs.
