This supplements the [Android native acceptance](android-native.md) and [Apple native acceptance](apple-native.md). Official release hashes establish provenance for **two** previously opaque inputs. No SDK or validator was executed, no build or account was used, and no sibling repository was modified. Free verify points remain encouragement/display with no product or consumption plan.

## Packaged Go EVM AAR: static metadata and vulnerability scan

Both app `evm.aar` copies have SHA-256 `28a8f91311b94b0ffaeea61620fa065633d0e8934b95c4250314c120775eb470`. Static `go version -m` on each ZIP member reports `go1.19.4`, `path gobind/gobind`, `mod gobind (devel)`, the Android target below, and **no embedded VCS revision**. This proves the Go compiler generation, not the N42 source commit or date of packaging.

The already-isolated `govulncheck v1.1.4` (SHA-256 `1ee8c00d1b46754fa1331f8bc4c3269172295bc0c2159e8e2e509feb14bc2027`) **can statically scan each extracted `.so`** with `-mode=binary -json`. All four scans completed without scanner error against database timestamp `2026-09-24T20:07:49Z`: each reports 113 distinct GO advisory IDs and 3,992 finding records at symbol scan level. The repeated records are symbol/module evidence, **not 3,992 distinct vulnerabilities or proof of exploitability**. JSON mode exits 0 even with findings. [Go's official scanner documentation](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck) states that binary mode uses symbol information, lacks source call graphs and can report included but unreachable code. It also cannot determine the exact application module version here because build metadata says `gobind (devel)`. The 113 IDs include old Go standard-library and dependency findings; they show a substantial unresolved dependency review, not whole-app exposure or a final release verdict. Exact per-ABI versions, hashes, scanner config, IDs, counts and empty errors are retained in [native-sdk-binary-scan-evidence.json](native-sdk-binary-scan-evidence.json). The `.so` data was read from temporary files that were deleted; no native SDK function was called.

## Rust MobileSdk: released source and real artifact matches

The supplier has [SDK-specific GitHub releases](https://github.com/n42blockchain/N42-rs/releases), with [`mobile-sdk-v0.2.2`](https://github.com/n42blockchain/N42-rs/releases/tag/mobile-sdk-v0.2.2) the highest public SDK tag found and a **non-prerelease** published 2026-01-16. The [official release API record](https://api.github.com/repos/n42blockchain/N42-rs/releases/tags/mobile-sdk-v0.2.2) gives the asset digests. Its tag resolves to [`2099ec735a658ba1db97c49b77a6c58c1fc82920`](https://github.com/n42blockchain/N42-rs/tree/2099ec735a658ba1db97c49b77a6c58c1fc82920). The public release asset `mobile-sdk-android.aar` digest is `97ab0b5e9665998f4387e09b812db4b05116ab9d49244182ccd2e8a1cba75646`, **exactly the app's** `android/app/libs/mobile-sdk-android.aar` (compile only). The public `mobile-sdk-ios.tar.gz` digest is `bcc3b974933a9bbab8a1f4e50172a79abdd1ccd8cbe9d335485f452f32248a0c`; downloading it in memory and checking its member found `ios-arm64/libmobile_sdk.a` SHA-256 `2c39c2d4870233c6af2c2280514c236f50eec3620ac030e8d1c80b66dbdfc745`, **exactly the app's** iOS device library. The bundled iOS header is byte-identical to the tag's header and includes `gen_block_verify_result_c`. Thus source/release provenance for these two app inputs is established by official asset digests and inner-library comparison, although the app's combined simulator slice was not matched.

The **packaged runtime** `plugins/flutter_mining/android/libs/mobile-sdk-release.aar` is SHA-256 `784783d758533826a768bc0697525d9b28caa857a3f4819707877fb790d6b254`. It lacks Android `genBlockVerifyResult`. Its hash matches **none of the Android AAR assets** listed by the supplier's public SDK releases inspected (`v0.2.2`, `v0.2.1`, `v0.2.0`, `v0.1.0-rc.*`). The v0.2.2 tagged [`build-aar.sh`](https://github.com/n42blockchain/N42-rs/blob/2099ec735a658ba1db97c49b77a6c58c1fc82920/crates/n42/mobile-sdk/build-aar.sh) exports `genBlockVerifyResult` and builds arm64/x86_64, so the app's current compile/runtime API split would be resolved by using one verified release AAR at runtime **if** integration checks pass. This is an upgrade candidate, not an implemented replacement. Preserve all five app-called Android methods and iOS `gen_block_verify_result_c`; check method descriptors, JNI loading, 16 KB packaging/device runtime, R8, signing, validator behavior without live production credentials, and the existing 32-bit capability issue before distribution.

The tag includes `Cargo.lock`, [`release-mobile-sdk-android.yml`](https://github.com/n42blockchain/N42-rs/blob/2099ec735a658ba1db97c49b77a6c58c1fc82920/.github/workflows/release-mobile-sdk-android.yml) and [`release-mobile-sdk-ios.yml`](https://github.com/n42blockchain/N42-rs/blob/2099ec735a658ba1db97c49b77a6c58c1fc82920/.github/workflows/release-mobile-sdk-ios.yml). A rebuild path is an isolated checkout of this exact tag with its lockfile and scripts, then comparison to release asset hashes. The published workflows use floating `stable`, `cargo install cargo-ndk/cargo-lipo/cbindgen`, floating runner/actions, and the script invokes Cargo without `--locked`; these do **not** promise byte-for-byte rebuilds without recovering exact CI toolchain/dependency versions. The official release binaries are therefore the stronger current provenance anchor. General node tag `n42-v0.9.1` is not a substitute for the SDK-specific release: its mainline source lacks the iOS block-result API.

## Go SDK: released project source is not a verified replacement binary

The public `N42-gov5` tag [`v5.7.906`](https://github.com/n42blockchain/N42-gov5/releases/tag/v5.7.906) is a project release candidate. The **current public remote** tag peels to [`5083c29735acfc7023ab1fbbd6d6527b7b97cbae`](https://github.com/n42blockchain/N42-gov5/tree/5083c29735acfc7023ab1fbbd6d6527b7b97cbae) (2026-08-20), corroborated by GitHub's release page. The local checkout's same-name tag instead peels to `0ce8e74bb3a627365b1b6c705b9ddfdfd68af073`; it is stale or was moved upstream, so the local tag must **not** be used as the canonical release identity. The remote commit is already readable locally without fetching. Its `cmd/evmsdk/common.go` retains `Emit(jsonText)` and `start`/`blssign` dispatch, the app-called API. It has `go.mod` requiring **Go 1.25.7** and `go.sum`, plus a [`Makefile` mobile target](https://github.com/n42blockchain/N42-gov5/blob/5083c29735acfc7023ab1fbbd6d6527b7b97cbae/Makefile) and Android/iOS sample build instructions. This is released **project source**, not an identified `evm.aar` release; no official Go mobile AAR digest or matching source revision for the packaged Go 1.19.4 binary was found. The generic release does not prove its Go SDK paths are an accepted app replacement.

The tag's Makefile Android command targets **arm only** (and API 23); the app ships arm64-v8a, armeabi-v7a and x86_64. The sample Android instructions target arm64 and explicitly describe multi-ABI invocation, but use `gomobile`/`gobind @latest`; the Makefile also does not pin gomobile or the Go patch toolchain. A reproducible candidate requires an isolated checkout of an approved tag, the tag's `go.sum`, a reviewed patched Go toolchain, pinned gomobile/NDK inputs, all shipping ABIs, source/module and binary vulnerability scans, recorded output hashes, and integration checks. None was built here. Replacing the 1.19.4 AAR with untagged main or merely the newest node tag would make an unverified behavioral migration.

## Legacy V1 reachability and removal condition

`evm.aar` is currently **reachable on Android**. `lib/core/providers/core_providers_security.dart` defaults `miningUseV2Provider` to true but restores a persisted preference from `SPUtil.getMiningUseV2()`. `lib/features/home/setting/setting_home_page.dart` exposes a switch that can set it false. `lib/features/home/home_page.dart` then selects `MiningHomePage` for the mining tab. `MiningHomePage.initData()` calls `MiningUtils.initEvmSdk()` and `startMining()`, leading through `lib/features/mining_v1/utils/mining_plugin_utils.dart` → `FlutterMining.emit` → Android `FlutterMiningPlugin.kt` → `Evmsdk.emit`. V1 settings and deposit flow also call the same helper. Start honors a stored open-mining flag, but initialization/status and user-triggered V1 controls remain. The Earn card independently opens V2 and does not make V1 unreachable. `WalletSigner.evmEmit`/`Trustdart.evmEmit` expose a second native `EvmEmit`/`TransactionSignerHandler.kt` call path; a targeted Dart search found no production caller outside those wrappers, but that does not erase the live V1 route. iOS `flutter_mining` plugin handles only platform version, so its Dart `emit` route is not a working iOS equivalent; iOS MobileSdk V2 uses separate native wiring.

**Possible permanent dependency removal only if V1 is intentionally retired:** remove the user-selectable V1 route and migrate its persisted preference, audit saved mining/validator state and real wallet assets, then remove V1 `emit` callers and the second unused `EvmEmit` facade before removing both `evm.aar` copies, `evm-module`, compile/runtime Gradle edges and native imports. Preserve V2 verification, account data and keys. A source-only claim that V1 is obsolete is insufficient while the settings switch remains; no removal was done.

**Targeted logging risk in the candidate Go source:** `MiningPluginUtils.initSetting` sends `priv_key` in the `setting` JSON. The canonical released Go [`common.go`](https://github.com/n42blockchain/N42-gov5/blob/5083c29735acfc7023ab1fbbd6d6527b7b97cbae/cmd/evmsdk/common.go) logs the entire request value through `simpleLog` **before** dispatching `Setting`, and `simpleLog` prints to stdout plus debug logger while `isDebug` is true by default. The app passes an empty `log_level` that may subsequently disable debug, but cannot prevent this first pre-dispatch log in that source. This needs redaction before considering that Go tag as a replacement. The packaged Go 1.19.4 binary has no exact source mapping, so this is a source-candidate defect, not proof of the shipped binary's logging behavior. In the released Rust v0.2.2 `run_client`, the targeted log lines show the WebSocket URL and block/receipt/public-key data, with no observed private-key print in those lines; this was not a full logging audit.

## Decision and remaining evidence

The Rust **v0.2.2** assets provide a concrete official runtime AAR candidate and exact provenance for the app's compile-only Android/iOS device inputs. The Go AAR has an old compiler and many static advisory matches, while V1 remains selectable; it needs a separately reviewed upgrade or an explicit V1 retirement. Exact packaged Go source and runtime Rust AAR provenance, actual SDK resource use and server-side verification/point attribution remain open. The previously documented 32-bit MobileSdk guard is separate and was not changed here.

## Remediation order and acceptance boundary

After the ongoing Chat push lifecycle fixes are reviewed, align the Android runtime with the verified SDK-specific stable release and add a process-aware capability boundary for every native MobileSdk caller. Preserve the app's armv7 wallet/chat support and the working 64-bit SDK APIs; validate native loading, signatures, deterministic offline transaction/crypto behavior, R8 and release packaging. Static alignment alone does not establish 16 KB runtime acceptance.

Then assess and build the Go replacement from immutable released source in an isolated checkout using the patched pinned toolchain, with request logging repaired before any fixture credentials enter it. The existing V1 API contracts and offline cryptographic/protocol fixtures are acceptance gates. Do not treat a node release as a mobile-compatible replacement without this evidence, and do not remove reachable V1 features merely to eliminate a scanner finding.

Neither this source audit nor an SDK upgrade proves deployed validator behavior, earned-point attribution or store approval. Free verify encouragement points remain separate from actual wallet assets and require no invented product catalog or consumption rules.
