## What must be generated or built

The tagged Git tree has no `rust/target/` archive. `src/rust/bindgen/` and
`src/Generated/` contain only placeholders, `jni/proto/` has only
`.gitkeep`, and `jni/java/wallet/core/java/` contains only the hand-written
`AnySigner.java` and `GenericPhantomReference.java`. `jni/android/` has only
hand-written `AnySigner.c/h`; generated JNI C/Java and protobuf files are
absent. Thus a native **source** rebuild cannot skip the generation pipeline
or safely relink the published `.so` from an AAR alone.

1. [`tools/generate-files android`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/tools/generate-files)
   runs `codegen/bin/coins` from exact-tag `registry.json`,
   [`tools/rust-bindgen`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/tools/rust-bindgen),
   Ruby `codegen/bin/codegen`, comment conversion and pinned host `protoc`
   with two custom plugins. It generates JNI C/Java, C++/Java protobuf,
   C headers and Rust C++ bridge code. For Android it skips Xcode project
   generation; iOS/Swift target builds are unnecessary.
2. Rust tool script names `nightly-2025-12-11`, uses
   `-Z build-std=std,panic_abort`, `RUSTFLAGS=-Zlocation-detail=none`, and
   emits **four** `libwallet_core_rs.a` files for aarch64, armv7, x86_64,
   i686 Android with API-28 NDK clang. The root Rust workspace release
   profile is `strip=true`, `codegen-units=1`, `panic=abort`; the
   `wallet-core-rs` crate is `staticlib`/`rlib` with default coin features.
   A future bounded recipe can try `cargo build -p wallet-core-rs --locked`
   per target instead of building all workspace libraries; the resulting
   header/static archives must actually link and pass compatibility before
   this is accepted. Tagged scripts have **no `--locked`** and install
   floating `cbindgen --locked` (locks the latest selected cbindgen version,
   not its version number). Pin and record an exact compatible cbindgen
   version, Rust toolchain/target, and `codegen-v2` lock without resolver
   drift. `codegen-v2` also invokes Cargo without `--locked` in the tag.
3. [`tools/dependencies-version`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/tools/dependencies-version)
   names Protobuf 3.20.3 and nlohmann JSON 3.11.3, plus GoogleTest 1.16.0
   and libcheck 0.15.2. `install-dependencies` downloads/builds all of them,
   including host `protoc` and the repository's
   [`protoc-gen-c-typedef`/`protoc-gen-swift-typealias`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/protobuf-plugin/CMakeLists.txt).
   `cmake/Protobuf.cmake` compiles the **3.20.3 source** into the Android
   native target; it is not an opaque packaged protobuf `.so`. On Android,
   `cmake/StandardSettings.cmake` sets `TW_UNIT_TESTS=OFF` and
   `TW_BUILD_EXAMPLES=OFF`, so GoogleTest/libcheck are not required by the
   final Android CMake target. Retain the pinned JSON headers and protobuf
   source/plugins; omit test-only builds only after proving the scoped
   Gradle target does not request them. Host Protobuf release tarball and
   header/plugin hashes must be recorded because the tagged downloader
   names versions but does not verify archive checksums.
4. Tagged CMake calls `find_host_package(Boost REQUIRED)` and links
   `Boost::boost`, the **header-only** imported target. It does not name a
   prebuilt Boost `.so` or `.a` for the final link. The scripts use floating
   `brew --prefix boost`; the currently installed Homebrew header candidate
   is Boost **1.90.0_1** (`BOOST_VERSION 109000`), but the supplier's Maven
   producer Boost version and exact header closure are unknown. Pin a
   candidate header archive/tree hash and `BOOST_ROOT`; inspect compile
   commands to prove which headers were included. No fresh Trezor clone is
   needed; its C target is compiled from the pinned vendor tree.
5. [Android Gradle](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/android/wallet-core/build.gradle)
   pins JDK source level 17, AGP 8.8.0, Gradle 8.10.2, NDK
   `28.0.12674087`, CMake `3.18.1`, min SDK 23 and
   `TW_UNITY_BUILD=ON`. The isolated machine has NDK 27.0/27.1/28.2 and
   CMake 3.22.1/3.30.5, **not** the tag's 28.0/3.18.1; its installed
   system `protoc` is 33.4 rather than 3.20.3, and the named Rust nightly
   and cbindgen binary are absent. Any 28.2/3.22 candidate is a recorded
   toolchain change, not an unchanged supplier build. Bind Rust and CMake
   clang to one explicit NDK path; tagged `find_android_ndk()` chooses the
   first API-28 clang under a directory and need not match Gradle's NDK.

This is a **bounded Android-only** build route, not a one-object relink:
four Rust static archives, generated JNI/proto, vendored TrezorCrypto,
native Protobuf and the broad `src/` C++ source set still participate.
Wasm/iOS targets, Xcodegen, samples, docs publishing, and host test binaries
can be excluded from the candidate pipeline. Do not fetch unrelated platform
trees or silently substitute a prebuilt Java/proto API without comparing it
to generated JNI/proto output.

## Final link and packaging boundary

[Top-level CMake](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/CMakeLists.txt)
constructs Android `TrustWalletCore` **SHARED** from `src/`, generated
`jni/android/`, generated proto sources and JNI C++; per ABI it selects the
matching `rust/target/<triple>/release/libwallet_core_rs.a`, then links
TrezorCrypto, Protobuf, Android log and Boost headers. Add the narrow
Android-only `-Wl,-z,max-page-size=16384` plus
`-Wl,-z,common-page-size=16384` at that **final shared link**, retain RELRO
and original crypto. Record actual CMake/NDK commands, generated hashes,
static archive hashes and source/tool/license manifests. The tagged
`trezor-crypto/CMakeLists.txt` compiles C sources; its repository
`LICENSE` and `LICENSE-3RD-PARTY.txt` (retained SHA-256
`acebc15b086cea49799f5f86b1fc60afe82f99a0ece7ab37ccf3e0f1094df0a6`
and `231c51196b17515caf6aa3b8898e7e19dd87ec93c73f1282b3efae1a7b37363a`)
must travel with the maintained source/notice inventory.

Retain all four ABI `.so` members (arm64-v8a, armeabi-v7a, x86, x86_64),
Java `wallet.core.jni` package and descriptors, and the exact
`wallet-core-proto:4.8.4` companion until its generated API/serialization
is demonstrated compatible. A narrow AAR repack can preserve published
non-native AAR entry bytes and swap only the four newly linked `.so` if
JNI methods match; it remains a maintained rebuild with a new artifact
hash, not the official Maven bytes. Compare JNI exports/DT_NEEDED and
generated bindings to published `classes.jar`, run `javap` on every
app-called class, and verify Gradle selects only one Wallet Core AAR plus
the expected proto JAR. Publish/use a task-owned local artifact without
editing global Maven/Gradle caches.

## Smallest real Wallet Core JNI fixture

Use a disposable offline Android fixture whose `System.loadLibrary("TrustWalletCore")`
loads the **published** AAR and the maintained candidate in separate fresh
processes. Bind APK, AAR, ABI/member SHA, PID/maps and strict-16KB settings
to each run. With test-only keys and no RPC or account data:

1. Construct `wallet.core.jni.HDWallet` from the exact tagged
   [`TestHDWallet.testCreateFromMnemonic`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/android/app/src/androidTest/java/com/trustwallet/core/app/utils/TestHDWallet.kt)
   mnemonic/passphrase; compare mnemonic, entropy, 64-byte seed and
   `getKeyForCoin`/`CoinType.deriveAddress` outputs byte-for-byte. This
   exercises app `KeyManagementHandler` derivation through JNI, not Web3j.
2. Build a synthetic `wallet.core.jni.proto.Ethereum.SigningInput` using
   [`TestEthereumTransactionSigner.testEthereumTransactionSigning`](https://raw.githubusercontent.com/trustwallet/wallet-core/d40d24a63d92619167903369308bf0e2f7eb3a59/android/app/src/androidTest/java/com/trustwallet/core/app/blockchains/ethereum/TestEthereumTransactionSigner.kt)
   (fixed `0x46` repeated private-key vector, nonce 9, fixed destination,
   amount and gas), then call `wallet.core.java.AnySigner.sign` with
   `CoinType.ETHEREUM`. Compare the exact published test `encoded` bytes
   and a second EIP-1559 vector, plus the old/new `SigningOutput` bytes.
   This reaches Wallet Core native signing and the companion protobuf JAR.
3. The app additionally calls `TransactionCompiler.preImageHashes` and
   `compileWithSignatures` for Bitcoin P2WSH in
   `android/app/src/main/kotlin/ai/n42/www/walletcore/TransactionSignerHandler.kt:1063-1080`.
   Add a fixed synthetic UTXO case through that path for old/new serialized
   result parity before calling all app-used Wallet Core signing behavior
   preserved. The tagged `TestBitcoinSigning.kt` supplies fixed native
   `AnySigner` BTC cases, but it is **not** a TransactionCompiler oracle by
   itself.

Existing `android_native_smoke` BIP39/BIP32 coverage exercises Web3j, not
Wallet Core JNI, so it cannot satisfy this gate. Audit candidate and final
APK/AAB 64-bit `PT_LOAD` and GNU_RELRO alignment, ZIP layout and actual
strict-16KB loading separately from the synthetic cryptographic results.
No Wallet Core candidate was built or run during this preparation.

**True remaining inputs:** source tar/archive integrity for the selected
