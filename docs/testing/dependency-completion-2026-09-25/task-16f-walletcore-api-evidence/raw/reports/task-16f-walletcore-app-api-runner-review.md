# Wallet Core API two-device runner source review

**Verdict: HOLD — two bounded evidence/safety findings.** Reviewed app commit `1bd34e8e6849aebc925310475acdf448ade41e8f..4e4d68d567a1691eec204440500af775124b7886`, its appended report, five normal and five optimized no-device gate tests, and the already reviewed build3 APK/epoch. I did not touch a device, rerun the fixture, or edit tracked files. `git diff --check` is clean; the only unrelated tracked delta is the normal `pubspec.yaml` build-number bump.

## Findings

1. **P1 — Prove task-owned emulator identity before any mutation or install.** `run_walletcore_api_fixture.py:147-165` calls `prepare_strict("emulator-5560")` before any state/ownership read, and `prepare_strict` (`:68-77`) changes airplane/Wi-Fi and linker/package compatibility on whatever process currently owns that serial. The later `snapshot` validates SDK/ABI/page/offline, but neither device's snapshot validates AVD name, host emulator PID/port owner or the task launch receipt. For `emulator-5562`, `task-api26-emulator-readiness.md:18` expressly requires PID/AVD/serial validation before later installs; its `task-api26-avd/launch.json` records `N42_API26_ARM64_W`, PID 8313 and port 5562. A replacement emulator with the same SDK/ABI/page could pass and receive the APK. Add a read-only serial, AVD and owning-process/port check against the existing task receipts **before** strict setup or either install; record it in the receipt and require it on replay. A changed/dead owner should fail closed. Do not use the fixture app PID as the emulator PID. This is a gate ordering and ownership fix, not a device rerun request.

2. **P2 — Replayed installed-APK evidence is only a copied JSON digest.** The runner `run_device:98-107` genuinely pulls the installed APK, hashes it and rejects a mismatch at execution time. But standalone `verify_walletcore_api_fixture.py:225-281` accepts `pulled_apk_sha256` from the receipt without opening the retained `<serial>-installed.apk`, and does not validate the pull/other ADB `argv` fields against the serial, package and expected output path. The positive synthetic verifier test at `test_walletcore_api_runtime_gate.py:76-127` passes with no pulled APK artifact and command objects containing only `exit`/`stdout`, proving the replay blind spot. Thus a later missing/substituted pulled artifact, or a receipt assembled from mismatched command outputs, can still produce replay PASS. Require a task-contained recorded pull path and rehash those retained bytes in standalone verification; verify at least pull/install/start/snapshot command serial/path bindings and add a delete/substitute-pulled-APK replay control. The in-run hash check is sound, so this does not claim the runner would install the wrong APK during its own execution.
