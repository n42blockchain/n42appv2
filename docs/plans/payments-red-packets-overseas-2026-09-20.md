# 海外法币转账、红包与 USDT/USDC 支付设计

日期：2026-09-20。状态：方案草案，尚未接入真实法币渠道或部署红包合约。

## 1. 已确认范围与推荐决策

用户确认首批覆盖欧美及其他海外市场，数字货币优先 USDT / USDC。

建议采用三条独立资金路径，共用聊天入口、订单查询和收据：

1. **法币钱包 / 好友转账 / 法币红包**：优先评估 Nium 的获批消费者钱包方案；欧洲方案备选 Mangopay。资金由签约的持牌合作方按获批资金流保管，N42 提供业务编排、账本和聊天体验。
2. **数字货币转账 / 红包**：复用现有 N42 用户钱包；普通转账由用户签名，红包资金进入经过审计的专用合约。
3. **银行卡或银行账户买币 / 卖币提现**：优先接 Transak；需要更广覆盖和报价选择时再评估 Onramper 聚合，不在第一版同时直连多家。

Thunes 为后续跨境出款补充候选，不作为红包余额账本。上述是产品选型建议，不代表 N42 已获得任何支付机构的生产准入。

法币建议从 USD、EUR、GBP 的获批国家/通道开始，其他国家逐步开放；“海外市场”不是全球无条件可用。用户所在国、居住地、实名状态、币种、资金来源与合作方批准的场景共同决定可用能力。签约主体注册地尚未确定，不阻塞本文设计，但会影响最终供应商选择。

## 2. 第三方渠道分工

| 渠道 | 推荐用途 | 已核实的公开能力 | 尚需取得的确认 |
| --- | --- | --- | --- |
| Nium | 第一优先评估法币钱包、内部转账、银行出款 | 开发者资料列出多币种账户、内部转账、客户/钱包、出款和 webhook | 消费者钱包、个人间转账、群红包预留/拆分/退回是否获准；每个国家与签约主体的服务范围；资金保管及争议责任 |
| Mangopay | 欧洲钱包方案备选 | 钱包间转账 API；不同 OWNER 用户间转账可能需要强客户认证 SCA | 社交赠礼/红包业务是否获准；支持的主体与用户地区；如何合法授权后续领取和退回，不绕过 SCA |
| Thunes | 后续跨境出款扩展 | Money Transfer API 覆盖银行账户、移动钱包等收款渠道 | 所需国家、币种、个人汇款场景和回退政策；不能从“支持出款”推导为“支持储值红包钱包” |
| Transak | 第一版法币买入/卖出稳定币 | On-ramp / Off-ramp、支付方式/资产查询、实名流程、订单状态 | 实时国家×支付方式×币种×网络矩阵、N42 业务准入、报价与费用；这不是 N42 法币 P2P 钱包 |
| Onramper | 后续买卖币覆盖与报价聚合 | 聚合多个 on/off-ramp，支持能力查询与组件配置 | 实际开通渠道、费用、地区及资产可用性；不承担 N42 红包资金托管 |
| Stripe Connect | 不用于本方案的个人转账/红包资金池 | 官方禁止业务清单列出 peer-to-peer money transmission | 即便未来用于其他合规商业收款，也不能复用该收单流程包装个人红包 |

依据：[Nium 开发者资料](https://www.nium.com/developers)、[Mangopay 转账 API](https://docs.mangopay.com/api-reference/transfers/create-transfer)、[Thunes Money Transfer](https://docs.thunes.com/money-transfer/v2/)、[Transak 买入](https://docs.transak.com/products/on-ramp)与[卖出](https://docs.transak.com/products/off-ramp)、[Onramper 接入说明](https://docs.onramper.com/docs/getting-started)、[Stripe 业务限制](https://stripe.com/legal/restricted-businesses)。

### 商务准入的最小验证

提交给候选方审核的业务流程必须准确写成：消费者入金 → 自有可用余额 → 向另一消费者转账或创建限时赠礼 → 多人领取 → 剩余资金退回 → 提现。不能用“电商分账”替代描述。

必须明确：资金由谁保管、消费者是否各有受保护账户、红包预留余额如何实现、后续领取是否触发 SCA、退款到余额还是原支付方式、拒付损失与准备金由谁承担、平台倒闭/渠道关闭时资金如何退出。若渠道不支持预留或经批准的独立受保护红包子账户，则不开放法币红包；不以 N42 自建普通公司账户集中收款替代。

本方案不假定免实名、实时到账、免费提现或固定费率。询价时核对开户/月最低费、KYC、入金、内部转账、出款、换汇、退回、拒付及最低交易费用。银行卡支付方式只在供应商明确批准给该消费者钱包场景后开放，首版优先审核通过的银行入金。

## 3. USDT / USDC 资产和网络

USDT、USDC 默认出现在资产选择器；是否可发送由实际余额、支持网络、接收方地址和地区能力决定。默认显示不等于承诺每条链、每个地区都能买入或提现。

| 功能 | 建议首批网络 | 设计说明 |
| --- | --- | --- |
| USDC 转账、真实红包首发 | Base | 作为第一条红包网络，控制合约和回归范围。只接发行方核实的原生 USDC，费用以实际报价为准。 |
| USDT 转账 | TRON；Ethereum 作为已有资金兼容选项 | 必须明确显示网络及 TRX/ETH 手续费。用户已有哪条链的币，就在经支持且接收方兼容的同一链发送，不暗中跨链。 |
| USDC 兼容转账 | Ethereum | 供已有资产使用；不能把 Ethereum 地址余额误认为 Base 余额。 |
| USDT 红包 | 后续部署并审计对应网络合约后开放 | TRON 转账能力不意味着已有经过验证的 TRON 红包合约。UI 未就绪前明确显示暂不支持该网络红包。 |
| 更多网络 | 后续按需求增加 | Solana 等进入单独阶段，不在第一版混合部署多套合约。 |

USDC 的发行网络以 [Circle 官方列表](https://developers.circle.com/circle-mint/supported-chains-and-currencies)为准；USDT 的协议和合约地址以 [Tether 官方列表](https://tether.to/en/supported-protocols/)为准。Circle Mint 的 USDC 能力不能当成 USDT 入金接口；不向其发送 USDT 或未支持的桥接资产。

**资产唯一标识必须为网络命名空间 + 网络 ID + 合约/铸币地址**，symbol 仅用于显示。额度使用整数最小单位或精确十进制字符串，不使用 double。币种精度来自受审查注册表，不从任意客户端字段采信。

不默认跨链兑换。网络不匹配时提示选择正确网络或进入独立兑换流程；未来支持兑换时必须展示来源资产、目标资产、到账数量、全部费用、报价有效期并另行确认。

## 4. 用户体验

### 钱包首页

- 两个明确区域：`法币余额` 和 `数字货币`，不把 USD、USDT、USDC 合并成一个可用余额。
- 法币显示可用、处理中、红包预留；数字货币显示币种、网络、可发送金额与网络手续费。
- 账户切换后，法币客户、订单、红包和绑定地址全部按当前账号重新加载，旧账号页面不得继续操作。
- 本地已有钱包不能自动绑定给每一个聊天账号。用户显式选择钱包并证明地址所有权；法币客户绑定还需合作方实名与防重复开户规则。

### 好友转账

1. 选择收款人。
2. 选择 `法币` / `USDT` / `USDC`。
3. 选择可用币种、网络与资金来源；已验证收款资料优先，不依赖聊天文本中附带的任意地址。
4. 显示支付金额、手续费、对方实收和预计状态；换汇另行报价。
5. 使用本机认证确认，必要时进入支付方 SCA 或本地钱包签名。
6. 发出聊天收据；到账状态由支付后端或链上核验决定。

直接转账默认到账后完成，不再要求收款人点“确认收款”。需要对方主动领取的场景使用红包，两种交互不要混在一起。

### 红包

- 单聊：专属红包；群聊首版：等额红包。拼手气进入第二阶段，先确定随机分配、公平性和地区准入。
- 选择金额、人数、祝福语；建议默认 24 小时有效，可由产品配置。
- 金额必须先落实到合法预留余额或链上合约，之后才发送可领取卡片。
- 领取显示处理中/已到账，重复点击返回同一结果，不多扣钱。
- 法币未领取部分按获批流程自动释放或退回**原币种余额**；如用户需要退至银行卡，走单独提现/退款规则。
- 链上未领取部分由合约允许在到期后退回发出地址；配置代执行服务发起退回。没有链上交易确认前显示“待退回”，不能仅凭定时器写“已退回”。已发生网络费不承诺退回。
- 未完成必要实名或尚未绑定接收钱包：展示明确步骤，在完成前不宣称到账。

## 5. 资金与系统架构

```text
N42 Flutter：钱包 / 聊天 / 转账 / 红包
                 │
                 ▼
N42 Payment API：当前账号鉴权、能力查询、报价、订单和红包
                 │
       ┌─────────┼────────────┐
       ▼         ▼            ▼
法币 Adapter   On/Off-ramp   Chain Adapter
Nium 或        Transak      本地用户签名
Mangopay       后续聚合      已审计红包合约
       │         │            │
       └─────────┼────────────┘
                 ▼
状态回调 / 链上索引 → 对账与账本 → 查询接口 / 聊天状态通知
```

这是一套编排接口，不是一个混合资金池。法币账本与链上资产账本分开，跨币种变动必须有独立兑换记录。

### 服务边界

- `PaymentCapabilityService`：返回国家、币种、网络、交易类型、渠道、限额和真实可用状态。
- `PaymentProviderAdapter`：开户状态、入金、转账、出款、退回、查询及回调。只暴露供应商实际支持的能力；不能虚构通用 reserve 接口掩盖供应商缺失能力。
- `LedgerService`：双重记账、可用/预留/处理中余额、唯一订单及幂等约束。外部余额必须对账，不凭客户端“成功”增加余额。
- `RedPacketService`：资金落实、领取资格、名额分配、到期退回。替换现有 LocalRedPacketService，生产环境不回退到演示余额。
- `WalletIdentityService`：账号与网络地址的签名绑定、撤销、过期挑战及重放防护。
- `ReconciliationWorker`：处理漏回调、延迟确认、链重组、失败与人工复核队列。

### 接口草案

| 接口 | 用途 |
| --- | --- |
| `GET /payments/capabilities` | 查询当前用户实际可用功能 |
| `GET /payments/balances` | 法币及已同步链上余额，明确类别和网络 |
| `POST /payments/quotes` | 返回实收、费用、有效期及报价 ID |
| `POST /payments/transfers` | 使用报价和幂等键创建转账，不盲目重试出款 |
| `POST /payments/red-packets` | 创建红包及资金落实流程 |
| `POST /payments/red-packets/{id}/claims` | 原子领取、返回同一用户的同一结果 |
| `GET /payments/transactions/{id}` | 查询权威状态与收据 |
| `POST /payments/wallet-bindings/challenges` | 生成绑定当前账号和网络的签名挑战 |
| `POST /payments/wallet-bindings` | 验证所有权并保存显式授权绑定 |
| `POST /payments/webhooks/{provider}` | 服务端验签、去重，更新权威订单 |

普通请求以当前账号鉴权为准，不信任请求体中的 senderId。签名绑定包含应用域、账号、网络、地址、随机 nonce 和有效期；更新收款地址重新验证。

### 红包状态与不可破坏的约束

`CREATED → FUNDING_PENDING → FUNDED → CLAIMABLE → COMPLETED`

分支包括 `FUNDING_FAILED`、`EXPIRED → REFUND_PENDING → REFUNDED`；领取子订单有自己的 `RESERVED / SUBMITTED / CONFIRMED / FAILED`。

- 每个红包每个已授权账号最多一次领取；总已确认领取 + 未确认占用 + 待退回不得超过实际资金。
- 同一幂等键只创建一个资金动作。超时先查原订单，不自动创建第二筆出款。
- 回调重复、乱序不让成功倒退成失败，不重复记账。
- 收款网络、资产、地址以及领取权绑定到订单；聊天卡片只带业务引用，不带任何可直接提款的秘密。
- 群红包建议以发出时成员快照限定范围，领取时再验证当前成员资格；转发卡片不转移领取权。
- 对链上红包，领取授权必须绑定 chain、contract、packet、recipient、amount、nonce、expiry，并由合约验证和去重。后端仅判断业务资格，不能任意改走提款地址。
- 首版等额红包避免把区块时间当随机数。拼手气另行设计可审计随机分配与抽样/总额测试，再通过地区场景审核。
- 仅向足额且满足可用资金政策的余额发放红包。银行卡授权或异步银行扣款处理中不能直接视为无拒付风险的可转出现金。

私钥保留在现有用户钱包；普通 API 密钥、webhook 秘钥及代执行服务凭证放服务端隔离存储。正式支付授权与应用 FaceID 的本机解锁区分开来，不能用本机解锁替代供应商要求的认证。

## 6. 当前代码需要先补的基础

核查基线：主应用 `30c15ee27`。

- `lib/features/wallet/n42_wallet_bridge.dart` 当前按 symbol 查找币种，默认收款地址偏向 ETH/N；多链 USDT/USDC 必须改为显式 assetId、网络和对应收款地址。
- 当前部分金额传参/解析使用 double；红包接口总额也使用 double。真实支付前改为精确金额模型并提供迁移测试。
- `packages/n42_chat/lib/src/data/datasources/local/local_red_packet_service.dart` 是演示实现，不能直接接真实余额后称为正式红包。
- 现有手工 Tip 地址只是缺失绑定时的临时入口，正式好友付款应接入可验证的钱包身份绑定。
- 修改 Chat 必须进入其独立仓库；主应用同步 Git pin 和缓存镜像，不能只改镜像文件。

## 7. 分阶段实施与验收

| 阶段 | 工作 | 主代理验收标准 |
| --- | --- | --- |
| D0 当前设计 | 海外范围、渠道分工、现状检查、本文 | 已形成候选方案；未开通渠道、未使用真实资金 |
| P0 资金基础 | 精确金额、资产 ID、账号隔离、地址绑定、统一能力和订单模型 | 同名跨链代币不误选；换号不串余额/地址；重复请求只有一个订单 |
| P1 稳定币转账 | USDT/USDC 在白名单网络转账、收款码、费用、链上状态 | 测试网覆盖收发、余额不足、手续费不足、错链、重复广播、重启与双方收据；真实小额验收须另获授权 |
| P2 单链真实红包 | Base USDC 单聊/等额群红包、资金落实、领取、到期退回 | 合约审计；并发不超发、无法重复领取、转发不能盗领、金额守恒、故障恢复和退回可证明 |
| P3 买币/提现 | Transak 托管组件、地区能力、订单回调、异常恢复 | 沙盒完整流程；各首发国家实际开放，未完成订单不入账，不把买币包装成法币好友转账 |
| P4 法币钱包与红包 | 获批的 Nium 或 Mangopay 消费者方案，法币入金、好友转账、预留/领取/退回/出款 | 取得明确业务准入；沙盒覆盖全资金生命周期、SCA、对账、拒付、退款和渠道故障；生产按受控小额验收放量 |
| P5 扩展 | USDT 红包、更多网络/国家、拼手气、Thunes/Onramper 补充 | 按新增能力独立审核和验收，不因为原渠道通过就默认继承 |

商务准入可以与 P0–P2 并行；未获批时保留能力关闭，不构造假余额或“支付成功”。本次仅完成设计，不授权联系供应商、上传公司资料、开生产账户、收集用户实名材料或发起真实资金交易。

实施采用既有精简子代理流程：每步独占文件、只传所需上下文、运行相关测试、结果追加文档；主代理审查 diff 和资金状态证据后决定合入/返工。生产付款链路的每个阶段独立验收，文档中的建议不等于已实现能力。
